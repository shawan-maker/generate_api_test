## 原则 1：三阶段一致性

**职责划分**：
- **Stage 1 负责探测**——所有操作步骤都要**记录下来**
- **Stage 2 负责回放**——只回放，不做业务判断处理；回放成功后生成 UI 脚本来运行
- （UI 脚本阶段）与 Stage 1/2 同源运行

**总要求**：这三个场景下，**元素定位、输入数据、操作方法、断言方式**必须一致。最理想的情况是**一套代码、多处调用**（非强制，但为优化方向）；期间需要考虑**单页面多 tab、单业务项多输入项组合、各种特殊选择框**（radio/tree-select/cascader/date-picker/transfer-box 等）等特殊情况。

### 1.1 元素定位

Stage 1 尽量使用**「输入项文本 + 相对路径 + 属性」**的组合约束来定位：
- ✅ 允许：文本、相对路径、属性约束
- ❌ 禁止：全局 locator、绝对路径、编号（nth-of-type/序号索引）、坐标定位

目的：方便后续阶段（Stage 2 回放 / UI 脚本）按记录的 locator 稳定复现。

### 1.2 输入数据（分情况处理）

1. **自构造数据**（随机字符串、随机数等）：Stage 1 记录**构造方法**，Stage 2 **重新构造**
2. **点击选择的数据**（下拉框、选择框、transfer-box 等）：Stage 1 记录**完整的操作过程和对应 locator**，Stage 2 **直接回放**，不重新构造

### 1.3 操作方法

三个阶段的操作方法**理论上统一**（或者说就是同一套实现）。最多按阶段判断行为差异：Stage 1 需要探测（边探测边记录），Stage 2 及 UI 脚本阶段**直接执行**。

### 1.4 断言方式

三个阶段的断言方法**理论上统一**（同一套实现）。

## 原则 2：API 捕获与脚本生成

**职责划分**：Stage 2 回放成功后同时捕获 API 接口；Stage 3 生成 API 脚本并运行。

### 2.1 接口捕获与值关联匹配（三原则）

**总要求**：所有业务接口（主业务接口 + 前置接口）都能正常捕获。**尽量使用泛化的逻辑来匹配，少使用硬编码**，提高工具可用性。

不管什么 ID 值（随机生成的、无规律可预测的），匹配原则如下：

1. **值匹配**——当前接口需要的值，在**前面所有接口的响应**中查找值相同的字段，建立关联关系
2. **时间最早原则**——如果有多个接口的响应中出现相同的值，按**时间最早出现**的优先匹配（**与请求方法无关**）
3. **多级匹配（递归追溯）**——如果前面接口的**请求**中也有随机值（该值同样无法直接构造），则继续往前找该值的关联接口，原则同上。具体例子：
   1. 当前接口 1 使用 ID1，通过原则 1、2 匹配了接口 2（响应中有 ID1）
   2. 接口 2 的响应中有 ID1，但其**请求**中有 ID2——ID2 在后续脚本中同样无法直接使用，所以要继续找 ID2 的关联信息：通过原则 1、2 匹配了接口 3（响应中有 ID2）
   3. 接口 3 的响应中有 ID2，请求中如果还有 ID3，则重复第 2 步；如果请求中没有这种随机值了，则**直接建立关联关系取值即可**

### 2.2 API 脚本生成

捕获成功的接口转换为 API 脚本，核心两点：

1. **依赖关系**：前置接口和主业务接口的依赖关系**必须分析清楚**，且**都生成脚本**；前置脚本的**响应字段值提取作为后续接口的请求参数**
2. **测试数据生成**：其他测试数据需能**区分清楚**类型——随机值、加密值、固定值等
