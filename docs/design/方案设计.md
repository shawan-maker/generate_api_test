# API 自动化测试 · 方案设计（API_AI_test）

> 目标：给定一个控制台 URL + 账号，自动发现主要功能与全部请求接口/参数，自动生成增查改删（CRUD）业务流脚本，并把脚本、数据、函数导出成 Postman / Apifox 可直接导入的格式。
> 设计原则：继承 EcsCloud UI 自动化项目的「双塔知识库 + 调试→沉淀→复用闭环 + 通过=真成功」方法论，把它从"UI 元素"迁移到"API 接口"，并最大化复用 EcsCloud 已有资产。
> 本轮修订（用户 4 条反馈）：① 框架多项目化（estack 只是其中一个 profile）；② **API 层与脚本层彻底分离**；③ 最大化复用 EcsCloud 资产；④ 功能发现采用"前端探测→点击抓取→逻辑编排→状态校验"四步法。
> 本轮（第二轮）修订（用户新 4 条反馈）：① 多 profile 规划延后、先搭基础框架（"待实采"）；② 新增**有效组合发现器**（找能成功的规格组合）；③ 新增**前置依赖解析器 / Test Data Fabric**（解决 10+ 前置接口取值）；④ 新增**全局参数挖掘器**（跨模块识别并复用项目级参数）。新增三子系统见 §4.5 / §7.3 / §9.1。
> **第三轮修订**：完成两个实际环境的 P0 巡游探测，用实测数据更新方案（详见 §1.4/§1.6/§2.4/§12/§13/§14）。
> 配套：`项目结构.md`（目录与分层）、`实地勘探报告.md`（estack 实测，作为首个 profile 的参考样本）。

## 1. 背景与目标

### 1.1 为什么做

企业内部后台系统大多**没有 Swagger/OpenAPI 文档**（estack 实测全 503/404，已确认）。传统抓包工具（Charles / Postman Interceptor）只能看到"这一次传了什么"，看不到"还能传什么、哪些必填、枚举有哪些值"。本方案用**浏览器巡游 + 前端表单结构抽取 + JS 静态分析 + 多样本推断**四路证据汇聚，补齐参数完整性，再自动编排 CRUD 并导出。

### 1.2 原始四大需求映射

| 用户需求 | 落地设计 |
|---|---|
| 1. 语言尽量 Python | Python 3.11+ 单语言栈，venv 隔离（呼应 EcsCloud 的 node-v20 教训） |
| 2. 给初始 URL → 自动发现主要功能、扫出所有请求 URL/参数、自动完成 CRUD 脚本 | 自动发现层（四步法 + 三层 + 四路证据）+ CRUD 编排器 |
| 3. 全局参数抽取到参数文件 | 参数四层分层（env / globals / data / context），变量语法 `{{var}}` 与 Postman 一致 |
| 4. 导出 Postman / Apifox 格式 | OpenAPI 3.1（Apifox 首选）+ Postman Collection v2.1（带断言与变量脚本）+ `_业务流/` 目录 |

### 1.3 本轮新增反馈与应对（4 条）

| # | 用户反馈 | 方案应对 | 见章节 |
|---|---|---|---|

## 2. 设计原则升级（4 条反馈落地）

### 2.1 多项目化（反馈 1）

- 框架层（`discovery/ lib/ generators/ config/`）**项目无关**，一次写好，主要靠 `config/settings.py` 读 `active project` 驱动。
- 每个被测系统一个目录 `projects/<id>/`，含：`profile.yaml`（base_url、api_namespace、auth_mode、固定头、slider 类型、ui 框架、menu_api）、`nav_kb.json`（项目级导航覆盖，可选）、`kb/`（双塔知识库）、`api/`（API 层）、`flows/`（脚本层）、`tests/`、`data/`、`output/`。
- 新增一个被测系统 = **复制一份 profile 模板 + 跑发现**，框架代码与已有知识库完全不动。

> **范围调整（第二轮反馈①）**：多项目架构保留，但"具体要迁移哪些 profile、各 profile 的 SID/命名空间/滑块类型"属于**登录实采后**才能填的内容，本轮**不预先规划具体 profile**，先搭基础框架。新增 profile 的规划改为"待实采"——拿到真实页面后再逐个补 `profile.yaml`，框架与已有 KB 不动。

> **实测验证（第三轮）**：已完成两个环境的 P0 巡游——`estack`（syyhb 运营管理平台）和 `ecm-compute`（移动云弹性计算）。两个环境共用一套登录页（SID/滑块/登录 URL 相同），但 token 存储方式不同（localStorage vs cookie）、入口业务完全不同。框架层的 `lib/auth.py` 已实现兼容。多项目架构的正确性通过实际环境得到验证。

### 2.2 API 层 / 脚本层分离（反馈 2，重点）

这是本轮最重要的架构决定。把"接口是什么"和"怎么测它"拆成两层：

- **API 层 `projects/<id>/api/`**：按菜单两级目录组织（`一级主目录/二级子目录/<resource>.py`），每个端点生成一个"薄"可调用函数，**只负责拼请求、发请求、返回响应对象，不含任何断言、不含业务编排**。由 `generators/gen_api_layer.py` 从 IR 自动生成。函数统一 `from lib.api_client import ApiResponse, get_client`；运行期取函数用 `lib.api_client.get_fn(project_id, service, resource, crud)`。
- **脚本层 `projects/<id>/flows/` + `tests/`**：调用 API 层函数，做业务顺序编排、变量传递、真成功断言、状态校验、清理。

**为什么这样分**：同一接口要既能测正常也能测异常。例如"创建用户"函数，正常传 `name="AT_user1"`，异常传 `name=""` 期望 4xx/业务失败——**用同一个函数即可**，无需为异常另写一套。API 层越薄越通用，复用面越大（正常流、负向测试、契约 fuzz 共用）。

```python
# projects/estack/api/访问控制/用户管理/users.py —— API 层（两级目录, 薄, 无断言）
from lib.api_client import ApiResponse, get_client

def draco_create_users(c, **extra) -> ApiResponse:
    return c.request("POST", "/estack/api/estack/draco/v1/users", json=extra or None)

# 正常 / 异常 都用同一个函数
create_users(c, name="AT_user1")      # 正常
create_users(c, name="")              # 异常：空名 → 期望 4xx / success=false

# 运行期取函数（规避 ecm-compute 连字符包名导入问题）
from lib.api_client import get_fn
create_users = get_fn("estack", "draco", "users", "create")
```

```python
# projects/estack/flows/user_flow.py —— 脚本层（编排 + 断言 + 状态校验）
def create_and_verify(c):
    r = create_users(c, name="AT_user1")
    uid = extract(r, "$.data.id")
    # 通过=真成功：创建→回查能查到
    assert_crud_success(api, "user", "list", expect_id=uid)
    # 状态校验（反馈④）：创建后不只存在，还要看状态字段
    detail = api.detail_user(c, id=uid)
    assert detail.status in state_semantics.expect("createUser", "active")  # 来自 kb/state_semantics.json
```

### 2.4 功能四步发现法（反馈 4，核心方法论）

对**每个业务模块**，按下面四步把 UI 变成可测脚本（详见 §4）：

1. **功能面探测**：枚举该模块有哪些功能按钮，以及它们的输入属性（label / value / 必填标记 / 枚举选项 / 控件类型）。这是"有哪些能力"的地图。
2. **点击抓取**：对每个按钮模拟点击，拦截发出的 XHR，得到**准确的**请求 URL、方法、参数、body、响应样本。这一步拿到的是真实报文，不是猜测。
3. **逻辑编排**：理解并组织按钮之间的顺序——最基础的增查改删，以及其它按钮（启用/停用/激活/导出/绑定等）。框架用启发式自动建议顺序，但最终顺序由人审 + `function_order_overrides.json` 校正（"需要自己理解并组织"）。
4. **状态校验**：操作后不只看"记录存在"，还要看业务状态（如新增后状态是否变"激活/可用"；有的没有状态、有的状态字段名/取值不同）。状态知识入库到 `kb/state_semantics.json`。

> **实测验证（第三轮）**：两个环境 P0 巡游验证了四步法中的②步是行之有效的。但发现两个实际问题：
> 1. **新建表单触发问题**：ecm-compute 的多个模块（安全组、弹性公网IP、VPC、云硬盘）的"新建"按钮点开后没有触发任何 XHR —— 可能是因为普通员权限不足或"新建"直接走弹窗而非路由跳转。需要更智能的对话框检测（`el-dialog` 可见时等待其内部接口）。
> 2. **菜单项全是 `no-href`**：两个环境的菜单项都没有真实 href（纯 Vue router 跳转），只能通过文本精确匹配点击。ecm-compute 的菜单跨度大（分组后下级菜单在子页面才渲染），需要更灵活的菜单展开逻辑。
> 3. **list 占比过高**：ecm-compute 的 50 个端点中 list 占了 35 个（70%），create 只有 5 个。说明应在巡游时**更积极地触发新建表单**（不只是点击按钮，还要等表单内部的下拉选预加载等）。

## 4. 自动发现层（需求 2 核心，按四步法组织）

### 4.1 三层策略 + 信任分级

- **Level1 — 文档端点探测**（两个环境实测全 503/404，基本判死，保留兜底字典，新项目先探一遍）。
- **Level2 — 流量捕获（主力）**：Playwright 驱动页面自动巡游，拦截 XHR/fetch。巡游顺序：登录 → 抓菜单树（=Postman 目录）→ 逐模块进入页面。破坏性动作（删除/提交）默认只探测不执行，标记待人工确认。
- **Level3 — JS 静态分析（兜底）**：扒 JS bundle 里的 `/api` 字符串与 `rules` 校验规则，补出"UI 没点到但存在"的接口，标记 `trusted:false`，须人工确认才入库。

> **实测验证（第三轮）**：JS 静态分析和流量捕获各有适用场景：
> - **estack**（12MB 单 bundle）：JS 分析检出 508 条路径、28 个 service（远多于 P0 巡游的 37 端点），但缺少请求方法和参数的完整信息，只能作为"已知存在但未捕获"的接口清单。
> - **ecm-compute**（1.7MB 入口 shell + 懒加载 chunk）：JS 分析仅检出 17 条路径（入口 JS 不含业务逻辑），90%+ 的 API 路径位于登录后才加载的 chunk 中。仅靠 JS 静态分析无法覆盖。
> - **综合建议**：Level3（JS 分析）对**单 bundle SPA**（如 estack）能提前给出全貌规划；对**懒加载 SPA**（如 ecm-compute）无效，必须依赖 Level2 流量捕获。两者在 `probe_profile.py` 中已自动识别并容错。

### 4.2 四步法（对应 §2.4）

| 步 | 模块 | 产出文件 | 说明 |
|---|---|---|---|
| ① 功能面探测 | `lib/nav.py` + `discovery/form_extractor.py` | `kb/function_surface.json` | 枚举模块按钮 + 输入属性（label/value/必填/枚举/类型） |
| ② 点击抓取 | `discovery/playwright_crawl.py` + 拦截 XHR | `kb/function_request_map.json` | 按钮 → {method, url, params, body, 响应样本}，真实报文 |
| ③ 逻辑编排 | `discovery/function_mapper.py` | `kb/operation_order.json` + `function_order_overrides.json` | 操作 DAG（create→detail/update/delete；enable/activate 在 create 后；导出 leaf）+ 人审覆盖 |
| ④ 状态校验 | `discovery/state_check_learner.py` | `kb/state_semantics.json` | 操作后期望状态字段+取值；无则退化存在性校验 |

### 4.3 四路证据汇聚（无文档时补齐参数完整性）

纯抓包只能看到"这次传了什么"。四路证据互补：

1. **真实请求多样本**：同一端点多次采样，按参数出现频率反推必填/选填。
2. **前端表单结构抽取（① 的主力）**：Element UI 新建弹窗里，`label`=参数中文名、红色 `*`=必填、`option` 列表=枚举全集、`type`=数据类型。与 create body 字段模糊匹配补齐中文名+必填性+枚举。
3. **JS 校验规则挖掘**：`rules:[{required:true,message:'请输入实例名称'}]`、`pattern:/^[a-zA-Z]/` → 必填性、正则、提示文案，置信度记为 `inferred`。
4. **人工标注**（优先级最高）：巡游中漏传参数看后端报错反推（做成独立"参数补全专项"，不进主流程，避免脏请求）。

置信度分级 `confirmed / inferred / guessed` 写进导出的 description，团队在 Apifox 一眼知道哪些可信。

### 4.4 归并去重（merge.py）

- 路径里的 ID 自动参数化：`/api/vpc/12345` → `/api/vpc/{id}`。
- 同一端点多次采样，按参数出现频率反推必填/选填。
- 按 `method + path 模板` 去重，`service+resource` 归组（estack 已知命名空间，归并更精准）。

### 4.5 有效组合发现器（反馈②：找"能成功的规格组合"）✅ 已实现 `discovery/combo_finder.py`

某些创建操作输入是离散可选项（下拉/单选），组合空间大（如 5 项 × 每项 3-4 选项 ≈ 上百种），但后端隐藏约束使**只有少数组合能新增成功**（规格不兼容、配额限制等）。暴力穷举会产生大量脏请求与孤儿数据。采用**证据驱动的剪枝搜索**（`discovery/combo_finder.py`）：

1. **种子**：从已知成功样本或各字段 default/首个选项出发。
2. **错误码引导的局部搜索（关键）**：每次失败解析 `errorCode/errorMessage`，用 `_infer_hint()` 启发式定位报错字段，仅在该字段上换选项、其余保持不动——把失败局部化；若某字段所有候选都失败则该路死。
3. **正交/两两组合播种**：`_pairwise_sweep()` 对每对字段枚举其选项组合（其余固定为基线），覆盖全部两两交互，远少于穷举但能抓住交叉约束。
4. **缓存与回环**：每次 probe 结果写入 `kb/param_constraints.json` 的 `triedCombos`，重跑跳过已试；仅当之前能成功的组合现在失败（漂移）才重新搜。

**护栏**：优先走"校验接口"（`validate_fn` / 独立 check 端点，非破坏性）；无则走 `create→delete`（创建成功后立即清理）并打标 `destructive_probe:true`。所有请求须过"通过=真成功"红线（§8）。

**输出结构（已对齐实现）**：注意区分两种负面信号——

```json
// projects/<id>/kb/param_constraints.json（按 resource 归组）
{
  "resource": "add-instance",
  "validCombos": [ {"fields": {"flavor":"flavor-a","billing":"postpaid","region":"r1"}} ],
  "incompatibilities": [              // 真·交互冲突: 两值各自可行, 但该组合从未成功
    {"fieldA":"flavor","valueA":"flavor-b","fieldB":"region","valueB":"r2",
     "reason":"两值各自可行但该组合从未成功(交互冲突)"} ],
  "invalidValues": [                  // 全局无效值: 从未在任何成功组合中出现, G3 直接规避
    {"field":"billing","value":"prepaid"}, {"field":"flavor","value":"flavor-c"} ],
  "destructive_probe": false,
  "triedCombos": [ ... ]
}
```

> 关键设计点：`incompatibilities` 只记录**真·交互冲突**（双方各自可行、但组合从未成功），而**全局无效值**（如 `billing=prepaid` 在任何上下文都失败）单列进 `invalidValues`——避免把"某字段本身非法"误报成"与某字段不兼容"，否则 G3 会过度保守。详见模块自测 `python discovery/combo_finder.py`（mock 规则藏一组有效组合，验证算法能发现 3 个有效组合 + 1 个真交互不兼容 + 2 个全局无效值）。

## 7. CRUD 自动编排（基于 ③④ 步产出）

### 7.1 分类器（双路判定 + 人工校正）

1. REST 结构启发式：`POST /res`→create、`GET /res`→list、`GET /res/{id}`→detail、`PUT|PATCH`→update、`DELETE`→delete。
2. 关键词启发式：路径/operationId 含 `create|add|save|新增|创建`→create；`list|query|page|查询|列表`→list；`update|modify|编辑`→update；`delete|remove|销毁`→delete。
3. **人工校正层 `crud_overrides.json`**（优先级最高）。

### 7.2 依赖图与变量传递（基于 ③ 顺序）

- create 响应提取主键 → `context` → 供 detail/update/delete 消费（见 `x-kb-depends-on`）。
- 提取规则入库（`$.data.id`、`$.id`、`$.data.*Id`、`$.result.uuid`…）。
- 都匹配不到时，用"创建前后 list diff"定位新增行主键（对应 UI 的列表轮询，稳）。
- 顺序由 `operation_order.json` + `function_order_overrides.json` 决定，**人类审查是最后一道关**（反馈④ step3："需要自己理解并组织"）。

### 7.3 前置依赖解析器 / Test Data Fabric（反馈③：解决 10+ 前置接口取值）✅ 已实现 `lib/resolver.py`

以"添加云主机"为例：UI 操作要填近 20 项，意味着 API 实现前需先调 10+ 个前置接口取回响应值（规格/镜像/网络/密钥/安全组/资源池…）才能成功。抽象为**前置依赖解析器**（`lib/resolver.py`），与 §2.2、§4.5 协同：

- **依赖清单声明式**：`DepSpec` 描述目标 create body 的每个参数槽——`literal`（来自 `{{var}}`/字面量）、`list`（调 API 层 `get_fn` 取取值池后抽取）。
- **运行时解析**：`resolver.provide(deps, ctx)` 按依赖图逐个取值；`list` 槽用 `get_fn` 调 API 层，按 `jsonpath` 从响应抽取取值池（优先 `jsonpath_ng`，缺失时回退内置 `$..key` 抽取器）；抽出的取值**回写 ctx**，供后续 `{{var}}` 引用（依赖图传递）。
- **套用 G2 组合约束**：若 `list` 槽标记 `combo_field`，加载 `kb/param_constraints.json`，剔除 `invalidValues` 与"与已选值冲突"的组合值（§4.5）。
- **上游值优先（ctx 透传）**：已在 ctx 中解析过的值直接透传、不重复拉取——这正是"10+ 前置接口"的图传递语义。
- **前置接口结果不落地成独立脚本**，作为取值节点被最终接口消费；异常路径也好测——把某前置值故意传错即覆盖"无效规格"失败用例。

```python
# 声明式依赖(替代 20 行硬编码)
deps = [
    DepSpec("projectId", kind="literal", value="{{projectId}}"),
    DepSpec("vpcId",    kind="list", service="vpc",   resource="vpc",    crud="list", jsonpath="$..id"),
    DepSpec("subnetId", kind="list", service="net",   resource="subnet", crud="list", jsonpath="$..id"),
    DepSpec("imageId",  kind="list", service="img",   resource="image",  crud="list", jsonpath="$..id"),
    DepSpec("flavor",   kind="list", service="flavor",resource="flavor", crud="list",
            jsonpath="$..id", combo_field="flavor"),     # 受 §4.5 约束
    DepSpec("region",   kind="list", service="region",resource="region", crud="list",
            jsonpath="$..id", combo_field="region"),     # 与 flavor 冲突时自动剔除
]
body = Resolver("estack", call_api=make_call_api, ctx={"projectId":"P-001"}).provide(deps)
# -> {'projectId':'P-001','vpcId':'vpc-1','subnetId':'sub-1','imageId':'img-1',
#     'flavor':'flavor-a','region':'r1'}  (flavor-b+region=r2 的冲突组合被自动拦截)
```

> `call_api` 可注入（离线用 mock），故 Resolver 可独立验证：`python lib/resolver.py` 自测覆盖"前置取值组装 body"与"G2 约束拦截冲突 region=r2"。详见 §4.5 的 `param_constraints.json` 与 §9.1 的 `context.json`。

## 8. 通过 = 真成功 + 状态校验（API 版红线）

### 8.1 真成功标准

| 操作 | 弱断言（会假通过） | 真成功标准 |
|---|---|---|
| create | HTTP 200 | 回查 list/detail 能查到 |
| update | HTTP 200 | 回查 detail 字段值 == 新值 |
| delete | HTTP 200 | 回查 404/空，或 list 中不存在 |
| 异步任务 | HTTP 200 | 轮询状态字段到终态 |

**API 特有假通过必须堵**：HTTP 200 但 body 里 `success:false` / `errorCode` 非空。estack 响应形如 `{traceId,success,message,errorCode,entity}`，断言必须校验 `success==true && !errorCode`。

### 8.2 状态校验（反馈④ step4 固化）

很多业务操作"记录了"不等于"成功了"。例如新增用户后状态要变"激活/可用"，新增资源后要"正常"才能算真成功。`state_semantics.json` 记录每个操作的期望状态：

```json
{
  "createUser":  { "verify": "detail", "status_field": "status", "expected": ["active", "可用"], "in_progress": ["creating", "初始化"] },
  "createVpc":   { "verify": "detail", "status_field": "state",  "expected": ["available"], "in_progress": ["pending"] }
}
```

断言时：先校验存在（8.1），再读 `status_field` 与 `expected` 比对；字段名/取值各业务不同，**首次发现时由框架学习、人工确认入库**。无状态字段则退化为存在性校验（不影响 8.1）。

## 9. 参数分层（需求 3，按项目存放）

四层，优先级从低到高覆盖：

```
projects/<id>/profile.yaml        项目级：base_url / api_namespace / 固定头(SID) / 凭据(env var 引用)
projects/<id>/globals.yaml        全局业务常量：region / zone / 默认规格 / 默认网段 / 资源前缀

```

**刻意设计：变量语法统一用 `{{var}}`，与 Postman 完全一致 → 导出零转换。**

### 9.1 全局参数挖掘器（反馈④：跨模块识别并复用项目级参数）✅ 已实现 `discovery/global_miner.py`

并非所有参数都该进 `globals.yaml`。`discovery/global_miner.py` 扫描全量 `api_catalog.json` + 响应样本，按以下信号提名候选全局参数：

1. **跨模块共现**：某字段名出现在 ≥`min_modules`（默认 2）个不同模块（service/resource）中 → 候选。
2. **取值稳定性**：该字段在多个响应样本中取值恒定 → 高置信"静态全局"。
3. **作用域命名启发**：字段名命中 `GLOBAL_NAME_HINTS`（`project*/tenant*/user*/account*/pool*/region*/zone*/org*/workspace*/domain*/vpc*/subnet*/cluster*/namespace*`）→ 直接提名。
4. **LLM 二次判断（可插拔）**：`llm_review(candidates)` 钩子可接入模型二审；默认走启发式，留接口即可切换。

分类与落盘：

| 类别 | 存放 | 例子 | 特点 | 判定 |
|---|---|---|---|---|
| 静态全局 | `globals.yaml` | 项目 ID、区域、租户、默认规格 | 一次配好长期不变 | 命名命中 + 取值稳定 |
| 动态上下文 | `context.json` | token、当前登录用户 ID、刚创建的各类 ID | 运行时填、过期刷新 | 认证态字段(`AUTH_LIKE`)或取值变化者 |

```python
res = mine_globals(catalog, project_id="estack")      # -> candidates / globals_draft / context_backfill
write_globals_yaml(res["globals_draft"], "projects/estack/kb/globals.yaml")
backfill_context({"userId":"U-100","token":"abcdefghijklmnop"},
                 "projects/estack/output/config/context.json")  # token 自动脱敏 -> "ab***op"
```

护栏：`backfill_context()` 对 `token/password/secret/apikey/cookie/authorization` 等字段按 `desensitize()` 脱敏（保留前 2 后 2 打码）后落盘；分页字段（`pageNum/pageSize/...`）直接排除。自测 `python discovery/global_miner.py` 同时扫描真实 estack catalog（已验证能识别 `tenantId` 为候选全局参数）。

- **Postman Environment** 从 profile/globals 生成，敏感值留空。
- **`_业务流/` 目录（强烈建议）**：排好序、变量已串好的 CRUD 链（创建→查列表→查详情→改名→删除→校验消失+状态）。导入 Apifox 后点"运行整个目录"即跑通闭环，也是把"通过=真成功+状态校验"红线固化进导出物。
- 附带 HAR / cURL，方便临时排查。

## 11. 补充能力（关键增强，用户要求全部纳入）

> 以下 8 项均为可落地设计，标注了"存放在哪 / 产出什么 / 何时触发"。

### 11.1 契约漂移检测（drift.py）
- **位置**：`lib/drift.py` + `kb/snapshots/`。
- **机制**：再次发现时 `diff` 两份 IR —— 新增端点 / 下线端点 / 参数增删 / 必填性变更一目了然。
- **价值**：API 项目相对 UI 的天然优势——DOM 变更难 diff，schema 变更极好 diff。让知识库能**自动更新**，不再只靠人反写。
- **产出**：`drift_report.json` + 报告里的高亮 diff 区块。

### 11.2 响应 Schema 基线（schema_baseline.py）
- **位置**：`lib/schema_baseline.py` + `output/schemas/`。
- **机制**：从捕获样本反向生成 JSON Schema 作为回归基线；后续响应结构变了立刻报警。
- **价值**：接口"悄悄改了返回结构"是 API 回归最常见的隐性破坏，基线一变即告警。
- **产出**：每个端点的 `*.schema.json` 基线 + 每次运行的 diff 判定。

### 11.3 资源命名前缀 + 孤儿清理器（orphan_cleaner.py）
- **位置**：`lib/orphan_cleaner.py`。
- **机制**：自动创建的资源统一前缀 `AT_20260818_xxxx`（沿用 EcsCloud 的 `AtSlb*`/`AtLsn*` 约定雏形）；配扫描器清理历史残留。
- **价值**：巡游/批量造数据后不留垃圾，避免污染被测环境、影响他人。
- **产出**：清理清单（先 dry-run 预览，确认后执行；默认隔离到 `_TRASH` 不硬删）。

### 11.4 鉴权集中管理 + 自动续期（auth.py + slider.py）
- **位置**：`lib/auth.py`（对应 EcsCloud `session.js` 逻辑移植）+ `lib/slider.py`（直接复用 `identify_gap.py` 原函数）。
- **机制**：token 过期自动重登 + 新鲜度缓存（避免每次请求都探活）；登录走**滑块验证码求解**（OpenCV 缺口识别 + Playwright 拖动）。固定 `SID`、语言头统一注入。
- **价值**：用例完全不关心鉴权细节，token 失效时框架自愈。
- **产出**：`output/config/context.json` 里的 token（脱敏存储）。

### 11.5 并发 / 串行分区
- **机制**：只读用例 `pytest -n auto` 并发提速；CRUD 链用 marker 强制串行（避免资源名竞争、互相删除）。
- **位置**：`tests/conftest.py` 定义 `crud` / `readonly` marker；RUNNERS 给出两条命令。
- **价值**：提速且不破坏"通过=真成功"的确定性。

### 11.6 敏感数据脱敏（desensitize.py）—— 安全红线
- **位置**：`lib/desensitize.py`，**所有捕获流量入库前必过**。
- **机制**：token / 密码 / 手机号 / 身份证等按规则脱敏（正则 + 字段名命中），入库样本均为脱敏副本。
- **价值**：捕获的流量里有真 token/密码，不脱敏就是安全事故。
- **铁律**：`profile.yaml` 里凭据只放 env var 引用（如 `${ESTACK_PASS}`），绝不落明文。

### 11.7 契约 fuzz（schemathesis，可选）
- **机制**：有 OpenAPI IR 即自动生成边界值/非法值用例（超长串、越界数、缺字段、错误类型），白捡一批异常场景。
- **位置**：`generators/` 或独立 `tests/contract/`；作为可关闭的增强。
- **价值**：零成本扩充异常路径覆盖（与 §2.2 的"同一 API 函数测异常"天然契合）。

### 11.8 AI 修复回路（ai_repair.py）
- **位置**：`lib/ai_repair.py`。
- **机制**：把 **API KB 相关端点 + 该用例失败历史（failure_ledger）+ 同资源已通过写法** 喂给 LLM，直接产出修复后的用例或定位建议。沿用 EcsCloud 方法论第 4 章第 7 条。
- **Prompt 模板**：
  ```
  你是 API 自动化工程师。接口知识见 kb/api_catalog.json 的 {endpoint}（参数/样本/CRUD分类）。
  目标：修复用例 <失败用例>，历史失败 <failure_ledger 该用例记录>。
  参考同资源已通过写法 <示例代码>。只输出修正后的 pytest 函数。
  ```
- **价值**：把"调试经验"沉淀成可复用的自动修复能力，进一步减少人力。

### 11.9 离线测试运行器（test_runner.py）—— 无外网替代 pytest
- **位置**：`lib/test_runner.py`，**沙箱无外网、`pip install pytest` 失败时的等价替代**。
- **机制**：用标准库完成与 pytest 同等的收集 + 运行，三种模式：
  - `collect`：收集 `projects/<id>/tests` 下所有 `test_*` 模块 / `Test*` 类 / `test_*` 方法（已验证 estack 8 + ecm-compute 8 用例，0 导入错误）。
  - `dry`：用真实 `get_client` 实跑，遇无服务器/网络错误优雅 `SKIP`。
  - `mock`：注入 `FakeResp` 用合成数据跑通"创建→查询→删除"编排接线（验证用例逻辑，不依赖服务器）。
- **pytest 兼容**：运行前在 `sys.modules` 注入极简 `pytest` shim（仅本运行器内生效，提供 `skip`/`fixture`/`created_id`），使生成的用例可 import；用户环境已装真实 pytest 时完全不受影响。
- **价值**：不仅能在无网环境"实跑 collection"，还会**真实暴露生成用例的接线缺陷**——曾由此发现 `test_black_white_list_detail` 把"无参配置接口"误当作"按 id 查实体"而传 `id=` 导致失败，已修复 `gen_pytest.py` 的 `detail_param` 推导（无路径参数时不再传 `id`）。
- **用法**：`python lib/test_runner.py --all --mode collect` / `--mode mock`。

## 14. 关键风险与对策（含实测验证）

| 风险 | 对策 | 实测验证 |
|---|---|---|
| 参数质量不可能一次到位（一批 `guessed`） | 置信度分级 + Apifox 里逐步校正回 `param_semantics.json`，每次校正即永久资产 | P0 巡游只捕获了基本端点，参数完整性需 P2（表单抽取）才能补齐 |
| 巡游对前端框架敏感 | estack 同为 Element UI，`base_nav_kb.json` 大段复用 EcsCloud | 两个环境均用 Element UI，菜单/按钮定位方法通用（el-menu-item / button:has-text） |
| 滑块验证码阻断登录 | 直接复用 EcsCloud `identify_gap.py` + Playwright 拖动（`lib/slider.py`） | estack 和 ecm-compute **滑块接口完全相同**，`human_drag` 在两个环境 headless 模式下均已验证通过 |
| 200 但业务失败（假通过） | 断言 `success==true && !errorCode` + 回查 + 状态校验（§8） | estack 响应 200 但 `success:false` 的情况已确认（登录接口可用该模式） |
| 敏感信息泄露 | 入库前强制脱敏（11.6），凭据只存 env var 引用 | `lib/catalog.py` 的 `desensitize()` 已在 P0 中使用，脱敏拦截 id/token/password 字段 |
| 破坏性操作误执行 | `AT_` 前缀 + 资源白名单 + 自动清理 + 高危模块黑名单 | ecm-compute 已有 `danger_blacklist: ['*delete*', '*remove*', '*destroy*']` |
| 多项目知识库串味 | 每个项目独立 `projects/<id>/kb/`，框架不持有项目特有知识 | estack 和 ecm-compute 的 api_catalog/captures/menu_tree 物理隔离，验证正确 |
| **登录语言不同（新增）** | `auth.py` 中自动切换语言，英文/中文登录页均兼容 | ecm-compute 登录页默认英文，按钮文本为 "Click to complete the authentication" / placeholder 为"Username"；已实现 `_switch_to_chinese()` |
| **token 存储位置不同（新增）** | 先读 localStorage，兜底读 cookie | estack 用 `localStorage.estackToken`，ecm-compute 用 cookie `accessToken` |
| **懒加载 JS 无法静态分析（新增）** | Level2 流量捕获作为唯一可靠手段，Level3 JS 分析仅对单 bundle SPA 有效 | estack 单 bundle 12MB → 508 路径；ecm-compute 1.7MB 入口 → 仅 17 路径 |
| **部分新建弹窗不触发 XHR（新增）** | 需要更智能的对话框侦测（`el-dialog` 可见时等待子组件加载） | ecm-compute 的 安全组/弹性公网 IP/VPC/云硬盘 新建弹窗点开后没有 XHR |
