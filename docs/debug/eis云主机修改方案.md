# 完整修改方案

## 批次一：状态机核心（治「假稳定」与「永久 disable 挂空」）

### 1.1 行状态权威读取 helper —— `_read_row_status`

- **路径**：展开目标行 dropdown 菜单 → 从菜单项 Vue 实例读 `command.row.status`（第 4 轮日志已实证该路径可得，同时顺带读 `qgaReady`）。读不到 → 返回 None。
- **为什么是源头**：不依赖状态列位置（不硬编码列索引），走的是 Element UI dropdown command 模式的通用数据通道；estack 行数据同构（第 4 轮 estack 启用操作日志同样有 `command.row`），读不到时静默降级，不破坏任何现有环境。

### 1.2 稳定等待升级 —— `_wait_row_states_stable` 重写

- **判定**：status **连续两次读值相同**（间隔 5s）**且** 菜单 enabled 集合连续两次一致，双条件同时满足=稳态。上限 180s（分钟级翻转覆盖：EIS 开机实测 ~18s，重装类更长的留余量）。超时不硬失败，记录 `state_wait_timeout` 继续走（让重试链兜底）。
- **关键设计修正**（吸取勘察教训）：**不预设“过渡态特征”**。此前想用「含 ing/中」判过渡，但 `Running` 含 ing、运行中含「中」——特征枚举必错。改用「值不再变化」本身作为翻转完成的证明：Stopping→Stopped 的任何值变化都会被轮询捕获。这是泛化的正解，且对任何状态机系统（estack 冻结/启用、未来模块）同构适用。
- status 读不到时退回现有「菜单集合两次一致」判定（现状行为，不降级）。

### 1.3 状态×按钮矩阵 + 转移边采集（写入 ui.json，Stage 2 暂不消费）

- **`state_button_matrix`**：每个稳态 settle 点，读 status + 扫菜单 → `matrix[status] = {按钮: enabled布尔}`。Running/Stopped 两态的可用清单自然形成（第 6 轮证明这个数据每轮都在产生，只是没记录）。
- **`state_transitions`**：每个行级操作执行前后各读一次 status → `validated[action]` 补 `row_state_before/row_state_after` 两字段；全局列表记 `{action, from, to}`（同三元组去重）。第 6 轮的「关机 Running→Stopped」「开机 Stopped→Running」边就是这样学到的。
- **跨轮累积**：Stage 1 启动时读旧 ui.json 的这两个字段，合并本轮新观测写入新产物（去重保序）。第 7 轮带着第 6 轮的矩阵跑，您已确认的「逐轮补全」节奏。
- **产物格式**：纯记录字段，无格式要求（您已确认），挂在 ui.json 顶层。

### 1.4 状态感知调度器 —— `_retry_state_blocked_ops` 升级为 `_state_aware_reconcile`

核心算法（循环式，替代现递归重试）：

12345678910111213

```
每轮 reconcile：
1. settle（1.2 等待稳态）→ 读 status + 扫菜单 → 采集进 matrix
2. R1 直接执行：pending 中「当前状态下已启用」的 → 逐个以业务身份执行
   （pending = 曾失败 + generic + 行级 + 未以业务身份成功过）
   执行后再 settle（该操作可能翻转状态）→ 回到 1
3. R1 恢复转移：无 ready 时，找「blocked pending 的需求状态」（matrix 显示
   该 pending 在状态 S 可用、当前状态不可用）+ 「已知转移边 from=当前状态 to=S」
   → 以恢复身份执行转移操作（intent=state_restore, triggered_by=首个需求操作，
   build_playbook Cascade-Order 已消费该语义）
   → 到达 S 后逐个尝试解锁的 pending：
       - 至少一个成功 → 边保持可用
       - 全部失败 → R2 该边标记耗尽（本轮不再走）
4. 无 ready、无可用恢复边 → 结束
```

复制

**R1-R4 规则**（已与您对齐的版本）：

- **R1 驱动性**：任何转移必须有驱动力（业务身份=待验证；恢复身份=有 pending 需要）——乒乓根治点：第二次「关机」若既已验证又无 pending 需求 Stopped，直接拒绝。
- **R2 边耗尽**：恢复转移到达后 pending 全失败 → 边本轮封禁，防矩阵误判反复横跳。
- **R3 业务唯一**：每操作业务身份每轮一次。
- **R4 恢复不限次**：关机/硬关机各把状态打到 Stopped，开机两次恢复均合法（各有新 pending 驱动）；已验证过的操作（如关机）可作为恢复手段再次执行。

**终止性与“防挂死”说明**（回应您对上限的质疑）：正常推演下每轮 reconcile 至少消费一个 pending（业务成功）或一条边（耗尽标记），pending 单调递减 → **自然终止，无覆盖上限**。唯一残余风险是环境异常（状态翻转卡死、点击假成功导致 status 永不变）→ reconcile 外层保留一个「轮数上限 12」**仅作挂死保险**，语义是「防 status 轮询 180s×N 无限挂」，不是限制业务覆盖；每轮 reconcile 的消费动作都会打日志（`[STATE-RECONCILE]` 签名），异常截断时日志可见原因。

**主循环集成**：现有两处调用点（成功后 + 收尾）替换为 reconcile；级联（新按钮发现）保留不动，reconcile 只接管「已入册被禁用」部分。
