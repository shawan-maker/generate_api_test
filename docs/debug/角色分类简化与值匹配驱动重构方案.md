## 一、现状问题

### 1.1 当前 9 角色体系

| 角色 | 当前语义 | 问题 |
|------|----------|------|
| `name` | 用户可读名称 | ✅ 合理，保留 |
| `mutable` | 可变字段 | ✅ 合理，保留 |
| `context` | 来自 `auth_profile.context_fields` 声明 | ⚠️ 仅靠字段名匹配，不考虑值 |
| `id_ref` | 以 Id/Ids 结尾的 ID 引用字段 | ⚠️ 本质是 context 的特例（值来自 create API 响应） |
| `test_value` | 降级分析识别的用户输入字段 | ⚠️ 与 generate 功能完全重复（都是按模式生成随机值） |
| `generate` | Phase B 发现需要随机生成的字段 | ⚠️ 与 test_value 重复 |
| `pre_api_ref` | Phase B 值匹配发现的前置 API 引用 | ⚠️ 本质是 context 的特例（值来自前置 GET API 响应） |
| `phase_ref` | 多 phase 操作中前置 phase 的引用 | ⚠️ 本质是 context 的特例（值来自同操作内前置 phase 响应） |
| `static` | 系统固定值 | ✅ 合理，保留 |

### 1.2 角色间相互拦截的典型 Bug

**Bug 链：迁移 `tenantId` 问题**
```
1. _classify_body_fields 识别:
   tenantId 在 auth_profile.context_fields 中声明 → 进入 context 规则
   但值 "5bcbffa..." ≠ create body 中的 "42ffdba..." → 降级为 static

2. Phase B trace_pre_api_dependencies 识别:
   tenantId 值 "5bcbffa..." 在 display-unit-tree 响应中找到 → 解析为 pre_api_ref

3. 应用 Phase B 结果时:
   保护列表: existing_role == "static" → SKIP! 不覆盖!

4. 最终结果: tenantId = static → 硬编码捕获值 → 环境变化后失败
```

**Bug 链：`policyIds` 问题**
```
1. _classify_body_fields: policyIds 不在 context_fields 中 → static
2. Phase B: 值是 hex_id 但无前置 API 来源 → generate_random
3. 保护列表: static 在保护列表中 → 不覆盖（旧版代码）
   → 后来把 static 移出保护列表 → 覆盖为 generate
   → 但 generate 不处理数组类型 → body["policyIds"] = "uuid-string" (应为 ["uuid-string"])
```

**根本原因**: 每个角色有独立的识别规则和保护规则，规则之间优先级交叉、相互冲突。

## 二、简化方案：5 角色

### 2.1 新角色体系

| 角色 | 语义 | 一句话定义 | 旧角色映射 |
|------|------|-----------|-----------|
| **name** | 用户可读名称 | 需要唯一性保证的名称字段 | name → name |
| **mutable** | 可变字段 | 每次运行需要不同值的描述类字段 | mutable → mutable |
| **context** | 上下文引用 | 值来自之前某个 API 响应或运行时状态 | context + id_ref + pre_api_ref + phase_ref → context |
| **generate** | 动态生成 | 无来源、按模式随机生成的值 | test_value + generate → generate |
| **static** | 系统固定值 | 原样保留、不需要变化的值 | static → static |

### 2.2 context 的统一 source 格式

所有"值来自某处"的情况统一为 context，通过 `source` 字段区分来源：

```python
# 来源 1: 登录上下文（原 context 角色）
{"role": "context", "source": "auth.tenantId"}

# 来源 2: 创建 API 响应（原 id_ref 角色）
{"role": "context", "source": "create.id"}

# 来源 3: 前置 GET API 响应（原 pre_api_ref 角色）
{"role": "context", "source": "display_unit_tree.entity_0_children_0_id"}

# 来源 4: 同操作前置 phase 响应（原 phase_ref 角色）
{"role": "context", "source": "generate.generate_password"}
```

运行时统一处理：根据 `source` 前缀决定查找方式：
- `auth.` → 从 `self.state[field]` 取值（auth_profile 提取的上下文）
- `create.` → 从 `self.state[field]` 取值（create 步骤提取的字段）
- `{api_id}.` → 从 `self.state[field_name]` 取值（前置 API 提取的字段）
- `{phase_id}.` → 从 `self.state[state_key]` 取值（前置 phase 提取的字段）

### 2.3 generate 的统一格式

```python
# 原来 test_value 的所有场景
{"role": "generate", "pattern": "email"}
{"role": "generate", "pattern": "phone"}
{"role": "generate", "pattern": "hex_hash"}
{"role": "generate", "pattern": "base64_encrypted"}
{"role": "generate", "pattern": "text"}

# 原来 generate 的所有场景
{"role": "generate", "pattern": "uuid"}
{"role": "generate", "pattern": "hex_id"}
{"role": "generate", "pattern": "random_int", "min": 10000000, "max": 99999999}
```

## 三、识别策略（按优先级）

### 3.1 优先级总览

```
优先级 1: name     → 字段名启发式 + 值特征（短可读字符串）
优先级 2: mutable  → 字段名启发式（description/memo/remark）
优先级 3: context  → 值匹配（在前序 API 响应中找到相同值）
优先级 4: generate → 值模式分析（hash/加密/邮箱/手机号/UUID）
优先级 5: static   → 兜底（以上都不匹配）
```

**核心原则**: name/mutable 靠字段名识别，context 靠值匹配识别，generate 靠值模式识别，static 是兜底。

### 3.2 新分类流程（替换 `_classify_body_fields` + Phase B）

```
输入:
  - body_sample: 当前操作的请求体
  - value_index: 全局值索引（前序 API 响应 + create body + create 响应 的扁平化值→路径映射）
  - create_body: 创建步骤的请求体（用于 name 和 mutable 的交叉验证）

输出:
  - field_roles: {field_name: {"role": ..., "source": ...}}

流程:
  for key, value in body_sample.items():
    # ── Pass 1: name ──
    if 字段名含 name/title/label 且 值是短可读字符串 (1-50字符):
      roles[key] = {"role": "name"}
      continue

    # ── Pass 2: mutable ──
    if 字段名含 description/memo/remark/note/content:
      roles[key] = {"role": "mutable"}
      continue

    # ── Pass 3: context（值匹配）──
    match = value_index.lookup(value, request_field_name=key)
    if match:
      roles[key] = {"role": "context", "source": match.source_path}
      continue

    # ── Pass 4: generate（值模式分析）──
    pattern = analyze_value_pattern(key, value)
    if pattern and pattern.role == "generate":
      roles[key] = {"role": "generate", "pattern": pattern.value_pattern}
      continue

    # ── Pass 5: static（兜底）──
    roles[key] = {"role": "static"}
```

**关键变化**: 
1. 不再有两阶段分类（先 `_classify_body_fields`，后 Phase B 覆盖）——**一次分类完成**
2. 不再有保护列表——不存在"先分类后被覆盖"的冲突
3. 值匹配在字段名匹配之前（context 优先于 context 字段名规则）

## 四、值索引（Value Index）设计

### 4.1 值索引构建

在 `_classify_body_fields` 之前，扫描所有可用的数据源，构建一个统一的值→来源路径索引。

```python
def build_value_index(
    pre_api_candidates: list,       # 前置 GET API 候选（含响应体）
    create_body_sample: dict,       # 创建步骤的请求体
    create_response_sample: dict,   # 创建步骤的响应体
    context_fields: dict,           # auth_profile 中声明的上下文字段
    replay_windows: dict,           # 操作时间窗口（用于时序优先级）
) -> ValueIndex:
    """
    构建值→来源路径的索引。

    数据源（按优先级从低到高）:
    1. pre_api_candidates 响应（init 窗口 + 各操作窗口内的 GET 请求）
    2. create 请求体本身（create body 中的值可作为自身的引用源）
    3. create 响应体（create 返回的 entity 字段）
    4. auth_profile context_fields（登录上下文）

    Returns: ValueIndex 对象，支持 lookup(value, field_name) 查询
    """
```

### 4.2 值索引条目结构

```python
@dataclass
class ValueIndexEntry:
    value: str              # 值本身
    source_api: str         # 来源 API 标识（"current_user", "display_unit_tree", "create" 等）
    source_path: str        # JSON 路径（"entity.tenantId", "entity[0].children[0].id"）
    field_leaf: str         # 路径叶子节点名（"tenantId", "id"）
    path_depth: int         # 路径深度（用于评分）
    timestamp: float        # API 调用时间戳（用于时序优先级）
    context: str            # 所属时间窗口（"init", "replay:迁移" 等）
```

### 4.4 噪声值过滤

```python
NOISE_VALUES = frozenset({
    "true", "false", "null", "none", "", "0", "1", "-1", "[]", "{}",
    "ACTIVE", "ENABLE", "DISABLE", "PENDING", "DELETED",
})

def is_noise_value(value) -> bool:
    """过滤过于常见、不能作为匹配依据的值。"""
    s = str(value).strip().lower()
    if s in NOISE_VALUES or s in {v.lower() for v in NOISE_VALUES}:
        return True
    if isinstance(value, str):
        if len(value) < 3:
            return True
        if value.isdigit() and int(value) < 100:
            return True
    return False
```

### 4.5 值查找与优先级排序

```python
def lookup(self, value, request_field_name: str = "", 
           current_action: str = "") -> Optional[ValueIndexEntry]:
    """
    在值索引中查找匹配项。

    匹配优先级（从高到低）:
    1. 响应时序优先: 越靠近当前操作的前序 API 优先级越高
    2. 字段名匹配: request body 字段名与响应路径叶子节点名一致 → 优先
    3. 路径深度: 更浅的路径通常意味着更直接的来源

    Args:
        value: 要查找的值
        request_field_name: 请求体中的字段名（用于消歧）
        current_action: 当前操作名（用于时序优先级）
    """
    value_str = str(value)
    
    # 处理列表值：取第一个元素匹配
    is_array = False
    if isinstance(value, list):
        if not value:
            return None
        value_str = str(value[0])
        is_array = True

    entries = self.index.get(value_str, [])
    if not entries:
        return None
    if len(entries) == 1:
        return entries[0]

    # 多源消歧评分
    def score(entry: ValueIndexEntry) -> float:
        s = 0.0

        # ── 优先级 1: 响应时序（越靠近当前操作越高）──
        # 使用 current_action 在 replay_windows 中的时间戳
        # 与 entry.timestamp 的差值越小越优先
        # 同一窗口内的 API 获得最高时序分
        if current_action and entry.context:
            entry_context_action = entry.context.replace("replay:", "")
            if entry_context_action == current_action:
                s += 100  # 同操作窗口内最高优先
            elif entry.context == "init":
                s += 50   # init 窗口（全局）次之
            else:
                s += 10   # 其他窗口最低

        # ── 优先级 2: 字段名匹配 ──
        if request_field_name and entry.field_leaf.lower() == request_field_name.lower():
            s += 30

        # ── 优先级 3: 路径深度（浅优先）──
        s -= entry.path_depth * 10

        return s

    return max(entries, key=score)
```

## 五、链式依赖追踪

### 5.1 问题场景

```
迁移 API body:
  tenantId = "5bcbffa731154b1da9c3dd41356088d8"
    ↓ 在值索引中查找
    → 找到: display_unit_tree 响应 entity[0].children[0].id

但 display_unit_tree 本身需要参数:
  GET /tenants/display-unit-tree-ignore-currentuser
  query_params: tenantId = "42ffdba38c58484f9be2bc1adf1672e6"
    ↓ 递归查找
    → 找到: current_user 响应 entity.tenantId
    → current_user 是无参数 GET → 链终止
```

### 5.2 链式追踪算法

在 `trace_pre_api_dependencies` 中，当前实现已经处理了 `depends_on`。链式追踪的核心改动：

```python
def resolve_chain(
    field_value: str,
    request_field_name: str,
    current_action: str,
    value_index: ValueIndex,
    used_apis: dict,        # 已使用的 API（防止循环 + 收集）
    seen_apis: set = None,  # 当前链中已访问（防循环）
    depth: int = 0,         # 当前递归深度
    max_depth: int = 5,     # 最大链深度
) -> Optional[dict]:
    """
    递归追踪一个字段值的来源。

    Returns:
        {
            "source": "api_id.field_name",
            "source_api": api_info,
            "chain": [...]  # 完整依赖链
        }
    """
    if seen_apis is None:
        seen_apis = set()
    if depth >= max_depth:
        LOG.warning(f"  链式追踪达到最大深度 {max_depth}，停止")
        return None

    entry = value_index.lookup(field_value, request_field_name, current_action)
    if not entry:
        return None

    # 防止循环依赖
    if entry.source_api in seen_apis:
        LOG.debug(f"  循环依赖检测: {entry.source_api} 已在链中")
        return None
    seen_apis = seen_apis | {entry.source_api}  # 不可变集合，防止跨分支污染

    # 记录使用的 API
    used_apis[entry.source_api] = entry  # 或完整的 api_info

    # 检查来源 API 本身是否有参数需要追踪
    source_api_info = entry.api_info
    if source_api_info:
        for param_name, param_value in get_api_params(source_api_info):
            if is_noise_value(param_value):
                continue
            sub_result = resolve_chain(
                str(param_value), param_name, current_action,
                value_index, used_apis, seen_apis, depth + 1
            )
            if sub_result:
                # 记录: 来源 API 的 param_name 依赖 sub_result
                add_dependency(source_api_info, param_name, sub_result)

    return {
        "source": entry.source_path,
        "source_api": source_api_info,
        "is_array": entry.is_array,
    }
```

### 5.3 树形/列表响应的特殊处理

部门树场景中，目标值是某个子节点的 ID（`entity[0].children[0].id`），不是根节点。

**当前 `extracted_fields` 的生成方式**：
`capture_apis.py` 在提取字段时已经扁平化了嵌套结构，生成了类似：
```json
{
  "name": "entity_0_children_0_id",
  "path": "entity[0].children[0].id",
  "type": "str"
}
```

值索引中已经有 `5bcbffa...` → `display_unit_tree.entity_0_children_0_id` 的映射，所以精确值匹配能直接命中。

**但需要注意**：如果树结构层级更深或子部门数量不同，提取路径可能不同。运行时提取需要能处理动态索引。

**解决方案**：在 pre_api 的 extract 中增加 `extract_strategy` 字段：
```json
{
  "name": "entity_0_children_0_id",
  "path": "entity[0].children[0].id",
  "extract_strategy": "first_valid_child",  // 标记这是"取第一个有效子节点"
  "parent_path": "entity[0].children",      // 父列表路径
  "filter": {"deleted": false}              // 过滤条件
}
```

运行时 `_extract_with_array_index` 识别 `extract_strategy`:
```python
if strategy == "first_valid_child":
    parent = extract_by_path(resp, parent_path)
    for item in parent:
        if all(item.get(k) == v for k, v in filter.items()):
            return item.get("id")
```

> **注意**: 这是一个可选增强。第一版实现可暂不添加 `extract_strategy`，依赖精确路径提取。只要 `extracted_fields` 中有正确的路径就能工作。

```python
def _build_body(self, step_def):

            body[key] = create_body.get(key, value)
            
        elif role == "mutable":
            prefix = self.config.get("test_data", {}).get("mutable_prefix", "Updated_")
            body[key] = f"{prefix}{self.ts}"
            
        elif role == "context":
            # 统一上下文引用：根据 source 解析
            source = role_config.get("source", "")
            body[key] = self._resolve_context_value(source, key, value,
                                                     role_config.get("is_array", False))
            
        elif role == "generate":
            # 统一动态生成：按 pattern 生成
            pattern = role_config.get("pattern", "uuid")
            generated = self._generate_value(pattern, role_config)
            # 保持原始类型
            if isinstance(value, list):
                body[key] = [generated] * len(value) if value else [generated]
            else:
                body[key] = generated
                
        else:  # static
            if isinstance(value, dict):
                body[key] = self._build_body_nested(value, field_roles, key)
            else:
                body[key] = value
    return body
```

#### 新增 `_resolve_context_value()` 方法

```python
def _resolve_context_value(self, source: str, key: str, default_value, is_array: bool):
    """统一解析 context 角色的值。

    source 格式:
      "auth.{field}"     → self.state[field]（auth_profile 提取）
      "create.{field}"   → self.state[field]（create 响应提取）
      "{api_id}.{field}" → self.state[field]（前置 API 提取）
      "{phase_id}.{key}" → self.state[key]（前置 phase 提取）
    """
    resolved = None
    
    if source.startswith("auth."):
        field = source.split(".", 1)[1]
        resolved = self.state.get(field)
    elif source.startswith("create."):
        field = source.split(".", 1)[1]
        resolved = self.state.get(field)
    elif source.startswith("create_body."):
        field = source.split(".", 1)[1]
        resolved = self.state.get("create_body", {}).get(field, default_value)
    elif "." in source:
        # api_id.field_name 或 phase_id.state_key
        parts = source.split(".", 1)
        field_name = parts[1]
        resolved = self.state.get(field_name)
    else:
        resolved = self.state.get(source)
    
    # 兜底
    if resolved is None:
        resolved = default_value
    
    # is_array 时确保数组
    if is_array and not isinstance(resolved, list):
        resolved = [resolved] if resolved else default_value
    
    return resolved
```
