## 四、r11 问题定案

### P-1（批九最高优先级）删除批内先行执行 → marker 行消失 → 6 操作连锁终败
- 证据链（时间线逐行）：14:15:14 重启 cascade 成功「云主机重启成功」→ 14:15:43 增量扫描发现新启用按钮含**删除**（退出运维模式后删除菜单解禁）→ 14:15:50 删除批内执行 → 14:16:06 捕获「删除成功。」→ 14:16:20 判定成功（**真删 marker 行 test672628**）→ 同批/后续批 14:16:23-14:16:42 依次执行 热迁移/重置密码/更新密钥对/修改Hostname/执行命令 → 全部「[F2-预检] 跳过: row_not_found —— marker 行不可见（搜索先行后仍未找到）」→ 14:16:48 查看详情 main 尝试同样 row_not_found → 6 项终败。
- 与批六 Q3 定案的呼应：**「删除排最后」策略失效三重根因（delete_actions 快照早于 marker 重收集 / _infer_action_role 仅精确匹配 / is_destroy_text 单源已建未接线）在 r11 首次实证真实代价**——r10 删除被运维锁死（skipped 未真删）掩盖了该缺口，r11 删除真删后 6 个依赖 marker 行的操作全部失去操作主体。
- 附加发现（机制性缺陷第二层）：删除成功后表格第一行锚点退化为其他行（克隆产物 test673250 等），增量扫描按 `.el-table__row:nth-child(1)` 发现的「新启用按钮」已不是 marker 行的操作，STATE-CHANGE 批执行却仍按 marker 搜索定位 → 必然 row_not_found。
- 修复方向（批九）：① STATE-CHANGE 批执行前按 DESTROY_KEYWORDS 将 destroy 类排批内最后（批六已建未接线的单源真正接线）；② marker 行存在性作为批执行前置检查——行不存在时终止本批并停止后续增量发现（或标记 run 收尾）；③ 删除操作成功后调度器应标记「行生命周期终结」，禁止后续对 marker 行的恢复尝试（14:16:42/14:16:59 两轮 reconcile 在行已删后仍空转）。
- 预期收益：6 项连锁中热迁移/重置密码/执行命令/更新密钥对/修改Hostname/查看详情在行存在时 r10 全部可成功，成功数可从 21 升至 26+；恢复/标签管理两项 reconcile 补救窗口也可恢复。

### P-2（沿用）恢复/标签管理 click_failed——三轮稳定型
- 恢复：仅 Paused 态菜单可见，main 窗口（14:01:38）行处于过渡态菜单未渲染；r9 靠更新密钥对驱动的 Paused→Running 偶然达成。标签管理：Running 态菜单项，main 窗口 VM 为 Stopped。
- r11 两者 reconcile 两轮（14:16:42/14:16:59）ok=0——叠加删除连锁（行已删，无法补救）。属 P-1 修复后大概率自然收敛项。

### P-3（沿用未触达）更新密钥对 el-select 值同步（r10 P3）

### B2（批八 P2 修复归因修正）hover 先行在黄金翻转窗未救回，成功捕获依赖时序
